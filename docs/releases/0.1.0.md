# Drop 0.1.0

Drop’s first release hosts invite-only, single-executable apps. Admins invite people, register nibrunner hosts and place apps on them. App owners upload a static Linux amd64 executable up to 90 MiB, configure it and follow its deployment in the reader, CLI or MCP. Drop itself runs on Linux amd64 and arm64.

S3 stores releases by SHA-256. AWS Systems Manager Parameter Store holds secrets, and each node agent reads the versions its apps need. The agent verifies the desired configuration and release content before replacing nibrunner’s configuration. Removing a placement stops the app and keeps its volume.

## Upgrading from a development build

1. Back up the project before starting 0.1.0. If it has multiple accounts, sign in as the original owner and record the `id` from `GET /api/drop/me`. Supply that ID in `DROP_OWNER_ID` alongside `DROP_OWNER_EMAIL` on the first upgraded start. Core 0.3.1 binds the account ID automatically when the owner is the only account.
2. Start the server normally to apply the migration. It creates a queue for committed SSM deletions and removes the shared storage flag from historical upload events. Rolling back to a development build requires restoring its pre-upgrade backup and reconciling any SSM changes since the backup.
3. When restoring a backup into 0.1.0, use `--hosted-restore` on its first start. This invalidates copied session credentials, unused upload links and node tokens. Nodes sign in again with their passwords. Restore discards the backup’s pending parameter deletions. Compare any queued names in a read-only copy of the backup with the restored app declarations and the current parameter store before deleting orphaned parameters. [Hosting and restore instructions](https://github.com/pocketcontext-labs/pocketcontext-drop/blob/v0.1.0/docs/hosting.md)
