# Drop

PocketContext Drop: a private, invite-only service that runs people's apps (one Linux executable each) on PocketContext-managed hosts, built as one Go binary. Derived from the PocketContext template (`docs/origin.md`), it serves people in hosted multi-account mode on `github.com/pocketcontext-labs/pocketcontext-core`, pinned to an exact tag in `go.mod`. This repository holds identity, policy, route allowlist and copy (`internal/droppolicy`), hooks and product server code (`internal/dropserver`), the runtime wiring (`internal/appconfig`), the CLI, the data model and the reader. The data model is still a placeholder collection, `apps` (owner, name, unique slug); later milestones replace it. Read README.md, docs/data-model.md and docs/hosting.md before changes.

- Keep the project to the database file, `storage/`, `drop.json` and the binary. Everything machine-specific (working copy, logs, local key, unpacked assets, tokens, OAuth state) belongs in the per-machine cache. Never write PocketBase runtime files (`.notify`, `auxiliary.db`, `types.d.ts`, backups) into the project folder.
- Never let the server open the synced database directly. Copy it in on start and write back only through consistent snapshots (`VACUUM INTO`) and atomic renames. Never overwrite a synced file that changed elsewhere; keep both and require an explicit `recover`. A database whose applied migrations this release does not ship is refused before PocketBase opens it (core's `CheckDatabase`, tested in `internal/appconfig/schema_test.go`); never edit or rename a migration that has shipped.
- Do not add dependencies on external tools, Python or network services at run time beyond the hosted SMTP server that core uses for sign-in email. Hooks and migrations run in-process: no `$os.cmd`/`$os.exec` or other `$os` calls (`internal/appconfig/hooks_test.go` enforces it; `sha256sum` and similar tools do not exist on every platform). There is no tunnel: do not add one back.
- Keep authentication on: Host check, own-origin CORS, ordinary `users` tokens on every API, including SQL and search. People use Drop only in hosted mode (`serve --hosted --headless --domain HOST --mcp`, `docs/hosting.md`): several accounts (`Policy.Accounts` = `AccountsMulti`), email sign-in, remote MCP with OAuth, plain HTTP behind a TLS-terminating proxy. The proxy options (`--hosted-http-address`, `--hosted-proxy-header`, `--hosted-proxy-networks`) live only in `internal/client/serve_hosted.go`; never trust a client-address header without an explicit `--hosted-proxy-networks`. Plain `serve` is the local single-account server on loopback, for developing the reader; there is no native public HTTPS mode. Never enable hosted mode by default or from project configuration.
- The hosted origin is default-deny: `internal/droppolicy/routes.go` `PublicRoute` is the whole allowlist, and `internal/droppolicy/testdata/public_routes.json` is its golden table (`routes_test.go`). A change to it is a reviewed diff (`-update-routes`), never widened to make a test pass. Record writes, `users` records, `/api/batch`, `/api/files/*`, the SQL and search reads (`/api/context/*`, which read whole tables and stay with the owner's local key) and every local administration route stay off it. The anonymous loopback route table `tests/testdata/public_routes.json` (`tests/public_routes.py`) is frozen; never widen it.
- Accounts: core creates the owner (`DROP_OWNER_EMAIL`, on `--hosted-init`) and any other account only when `Hooks.AllowSignIn` admits the address (`internal/dropserver/hooks.go`; until invites exist it admits nobody). `pb_hooks/account_access.js` accepts several accounts and lets core prune accounts that never signed in, but refuses to delete one that has. Every record belongs to an account: collection rules filter by owner (`owner = @request.auth.id`) and Go hooks set the owner from the request, so one account never reads or changes another's records; `Runtime.IsOwner` tells the owner apart, and core authorizes nothing between accounts. Hosted accounts all share one name: the reader shows email addresses. Never open a rule to anonymous requests.
- MCP tools: Drop will have exactly two, `drop_read` and `drop_write`, calling Drop's operations with the caller's own account; until then the endpoint lists no tools. Never add shell, filesystem or administration tools, and a new tool needs the owner's approval. The local key never leaves the private cache.
- Remote mode (`--url`) is a client only: it never resolves or creates a database, never starts a server and never reads the local key. It accepts loopback URLs only and stores a token, never a password.
- The SQL reader reads the live database and exposes only the columns listed in `server.json` `tables`, never auth collections, credentials or SQLite metadata. `build-tags.txt` is copied unchanged from pocketcontext-core and enables exactly the SQLite features tested in `internal/appconfig/sqlite_test.go` (its tailscale tags are unused here); do not add icu, userauth, allow_uri_authority, secure_delete, vacuum, foreign_keys, app_armor or os_trace, and keep the reader's denial of `dbstat`, `pragma_*`, `sqlite_schema`, FTS shadow tables and writes.
- Keep the vendored server in `internal/pocketcontext/` under its upstream name (its `database`, `sqliteuri` and maintenance packages live in pocketcontext-core). Review security fixes in PocketContext (see `docs/origin.md`), the vendored server (`internal/pocketcontext/VENDORED.md`) and pocketcontext-core and port them by hand. Never add a `replace` directive for pocketcontext-core; a core fix ships as a tagged core release and a pin bump here.
- Never introduce the retired product name that `tests/name_check.py` checks for: not in files, file names, messages, tests or the binary.
- Drop is Linux only (amd64 and arm64): CI runs on `ubuntu-24.04` and `ubuntu-24.04-arm`, releases build `linux_amd64` and `linux_arm64`, and `cmd/drop/main_other.go` (`//go:build !linux`) makes every other system's build refuse to run. Do not add macOS or Windows code, installers, CI jobs or release platforms. A future laptop client would be a separate pure-Go program (no cgo) calling Drop's API, not this binary. pocketcontext-core stays cross-platform for its other applications; the vendored `internal/pocketcontext/` keeps its upstream platform files.
- Tests use synthetic data in temporary folders. After changes run `make test` (Go tests with the tags in `build-tags.txt`, including the hosted tests built on `internal/droptest`, the launcher test and the release tests), `python3 tests/name_check.py --binary bin/drop`, `python3 tests/identity_check.py --binary bin/drop`, `python3 tests/public_routes.py --binary bin/drop` and `python3 tests/e2e.py --binary bin/drop` (`make e2e` runs all four); rebuild `ui/dist` first when the reader changes.
- Never commit `bin/`, `ui/dist`, databases, secrets, real data or machine-specific paths. The repository is private, but treat every commit as if it could be published.

## Identity

- `tests/identity_check.py` (`make identity`, CI and release) must keep passing: none of the template's name, repository, hello-world collection or default port (assembled from parts in that file) in file names, contents or the binary outside its allowlist (`docs/origin.md`), and no identity field in `internal/droppolicy/policy.go` at the template's value. Do not change its needles or logic; an `ALLOWED` entry needs a reason a reviewer can verify. The identity values (`drop`, `pocketcontext-drop`, port 8100, `account@drop.invalid`, OAuth scope `drop`) are persisted: never change one after the first release.
- Keep every change passing `make ui build test names identity e2e`, both browser tests (in CI) and the docs and skill accurate to the code.
